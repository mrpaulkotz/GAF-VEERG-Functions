# InputFields override mechanism (build-input-fields-json.ps1)

- Per-field override files live at `InputFields/_overrides/<Module>.json`, hand-maintained, never regenerated. Merged over generated output on every `npm run build:input-fields`.
- SEPARATE from enterprise defs in `Enterprises/<Enterprise>.json` (do NOT put input-field overrides there).
- `Merge-Override` does deep per-field merge (rewritten from old shallow whole-value replace):
  - Top-level keys starting with `_` are ignored (docs/schema/comments).
  - `InputCells` = map keyed by CellName; props shallow-applied onto matching ordered-dict field.
  - `InputTables` = map keyed by TableName; nested `Columns` map keyed by column key. Columns live under `Rows.Row.<key>` (RowsToCols) or `Cols.Column.<key>` (ColsToRows).
  - Unknown cell/table/column targets -> Add-ValidationWarning, UNLESS the
    override itself has `"ExcelExcluded": true` (see below) - then it's added
    wholesale instead.
  - Other top-level keys fall back to whole-value replace (backward compat).
- Override props are passthrough (Label, Group, Order, Hidden, UseDefault, Default, ...); can also override generated props like CellType.
- Example starter file: `InputFields/_overrides/Enterprise_PastureBeef.json`.

# ExcelExcluded (2026-08): fields that exist ONLY for the consuming web app
Some InputCells/InputTables (e.g. `Table_Input_Mortalities`,
`Table_Input_HerdTransfersIn`, `Table_Input_HerdTransfersOut` on
Enterprise_PastureBeef - part of the web app's herd ledger) have no Excel
cell/table backing at all; they're pure web-app fields. Mark these
`"ExcelExcluded": true` in the override. Because nothing in the generated
(Excel-derived) base model matches their name, `Merge-Override` used to log
"Override references unknown InputCell/InputTable '...'" for every one of
them on every build - noise, not a real problem, since the flag means "this
was never supposed to come from Excel." Fix: when the target isn't found in
the base AND the override has `ExcelExcluded: true`, the override object is
the COMPLETE field definition (not a patch) - it gets added directly into
Base['InputCells']/['InputTables'] (keyed CellName/TableName = the override's
own key) instead of warning. This is why the three ExcelExcluded table
overrides are written in the full generated-table shape (`MatrixType`,
`ColumnNames`, `Rows.Row.<col>.CellType`/`Options`) rather than the `Columns`-
patch shape used for adjusting an existing generated table - there's no base
to patch onto. Verified: `-WorkbookPath Enterprise_PastureBeef_WIP_v01.xlsx`
dropped from 3 "unknown InputTable" warnings to 0, and all 3 tables now
appear correctly in the generated `Enterprise_PastureBeef_InputFields.json`.

# Fixed-row Excel tables (Table_Input_DataQuality_*) via named-cell-style detection (2026-08)
Some `Table_Input_*` ListObjects (the 5 `Table_Input_DataQuality_*` tables:
Enterprise/Site/PastureBeef/PastureManagement/FertiliserApplications) are NOT
open user-add-a-row tables like the rest - their row set is fixed (a
predetermined list of scoring criteria, e.g. "Electricity purchased", "Fuel
used") and their first column ("Data type") is a read-only row IDENTITY
label the author typed directly, not a field. `Get-InputTables` used to treat
every ListObject uniformly (every column = an editable field, table = grow
as many rows as the user wants), so that label column was wrongly emitted as
a per-row free-text field and the actual fixed row list was never captured
anywhere in the output at all.
- Detection: this workbook already has a rich (72-entry) named-cell-style
  convention - EVERY genuinely editable or calculated-but-overwritable cell
  carries an "Input ..."-prefixed style (`Input text`, `Input select`,
  `Input number general calculated`, ...); fixed/display content uses a
  non-"Input" style (`Content normal`, `Content bold`, `Number display
  decimal`, ...). This is a far more robust signal than format or HasFormula
  (which can't distinguish "hand-typed label" from "hand-typed free-text
  field" - both look identical by format). Spot-checked directly via package
  XML style lookups before implementing: all 5 DataQuality tables' first
  column data cells = "Content normal"; known-good open-add tables
  (`Table_Input_LivestockSales`, `Table_Input_InorganicFertiliser_Brands`)
  have "Input text"/"Input select" on their first column - zero false
  positives on either side.
- Implementation: `Get-InputTables`'s ListObject loop checks ONLY the first
  column's representative body cell (`ListColumns[0].DataBodyRange.Cells(1,1)
  .Style.Name`); if it exists and does NOT match `(?i)^Input\b`, that column
  is excluded entirely from `ColumnNames`/`Rows.Row` (not emitted as a
  field), and its per-row text values (via `Get-FieldKeyFromHeader` for
  stable keys, same helper the named-range ColsToRows path already uses for
  row labels) are captured as a new `RowLabels` ordered dict (key -> display
  text), alongside `FixedRows: true` and `NumberOfRows`. Deliberately scoped
  to ONLY the first column (not "any non-Input column in any table") to
  avoid risking a false positive silently dropping a real field elsewhere in
  the repo that hasn't been individually verified.
- Verified end-to-end against `Enterprise_PastureBeef_WIP_v01.xlsx`: all 5
  DataQuality tables now emit `FixedRows: true` + the correct `RowLabels`
  (e.g. Enterprise's 6: "Liveweight sold", "Liveweight grown", "Manure
  produced", "Manure sold", "Percent income from liveweight sold", "Percent
  income from manure sold") with the "Data type" column gone from the field
  schema; `LivestockSales`/`InorganicFertiliser_Brands` unaffected
  (`FixedRows` absent, first column still a normal field).

# Cascading (dependent) select options
- Dependent dropdowns use validation like =INDIRECT("Table_..._" & SUBSTITUTE($E$7," ","") & "[Region]"). Parent driver $E$7 may itself be a passthrough formula (=X_Cell_Site_State).
- Resolve-ParentInfo follows passthrough formulas to find the true source cell w/ the list validation. It must follow BOTH cell-address passthroughs (=$X$Y) AND bare defined-name passthroughs (=X_Cell_Site_State). Fixed a bug where only address form was followed, leaving Options={} and DependentOn as a raw address (e.g. E7). Now DependentOn resolves to the named cell and Options are the nested per-parent lists ("n/a" for parent values with no child table).
- The concatenated-cascade branch was unified (removed the fragile single-SUBSTITUTE regex that mis-parsed nested calls, producing broken DependentOn like "SUBSTITUTE(SUBSTITUTE(SUBSTITUTE(F63"). Now: Get-InnerCallArg pulls the INDIRECT arg, Split-TopLevelAmpersand isolates the single non-literal driver seg + prefix/suffix literals, then Resolve-CascadeDriver peels nested SUBSTITUTE(inner,"from","to") wrappers to the bare ref + ordered (innermost-first) sub pairs. Each parent value is normalised with the SAME sub chain to build <prefix><norm><suffix>; Options are keyed by the normalised value (matches Excel's SUBSTITUTE, e.g. "Sardines (whole)" -> "Sardineswhole"). DependentOn prefers the sibling table-column key (e.g. Ingredient1). Helpers: Split-TopLevelComma, Resolve-CascadeDriver.
- Header-range structured refs: =INDIRECT("Table[[#Headers],[ColA]:[ColB]]") now resolve. Resolve-StructuredOrEvaluated detects the [#Headers] range form (checked before the single-column regex, which its nested brackets defeat) and Get-ListObjectHeaderRangeValues returns the header labels of columns ColA..ColB from the ListObject (Worksheet.Evaluate is unreliable for cross-sheet structured refs).

# Date field typing
- Set-DateFieldTypes runs before ConvertTo-InputFieldsModel returns: any field whose KEY contains 'date' (case-insensitive) with CellType 'number'/'text' becomes CellType 'date' (Excel stores dates as numbers so format detection misses them). Covers InputCells + table Rows/Cols columns. Leaves select/formula alone.

# Name field typing
- Set-NameFieldTypes runs right after Set-DateFieldTypes: any field whose KEY contains 'name' (case-insensitive) with CellType 'number' becomes 'text'. Root cause: Get-CellTypeByFormat falls back to 'number' when the representative body cell is blank, so free-text label columns (e.g. TransactionName in Table_Input_LivestockSales/Purchases) were mistyped 'number' whenever their sample cell happened to be empty. Leaves select/formula/date alone.

# PLANNED (2026-08-19, not yet implemented - build scheduled for tonight): conditional CannotOverWriteFormula
Motivating case: `X_Table_Result_ActivityPeriodEmissions_RowsToCols` columns
`CO2EEmissionsMethod1`/`CO2EEmissionsMethod2` (Enterprise_PastureBeef) have formula
`=IF(ISBLANK($D55), 0, IF(ISNUMBER(SEARCH("reporting", $D55)), Result_Enterprise_Scope1_Method2, "Enter value"))`
where `$D55` is that row's `EmissionsCalculationCycle` cell. Static `CanOverWriteFormula: true`
is too coarse: the SAME column needs a different overwrite decision on different rows (only
overwriteable when `EmissionsCalculationCycle` does NOT contain "reporting" - blank rows stay
overwriteable too, since blank never contains "reporting", no separate blank-check needed).

Design was worked out jointly with the developer of the consuming app (sibling package
`conversational-input`, which independently implements the real write path); this repo's
`scripts/create-test-excel-from-json.ps1` (`-Context Emissions`) mirrors that path purely for
local test-population, so both sides need the same change.

- Schema: add `CannotOverWriteFormula` as a conditional EXCEPTION on top of the existing static
  `CanOverWriteFormula: true`, e.g.:
  `"CO2EEmissionsMethod1": { "CanOverWriteFormula": true, "CannotOverWriteFormula": { "Column": "EmissionsCalculationCycle", "Contains": "reporting" } }`
- `Column` (NOT `Field`): every existing `Field` reference in this repo's overrides
  (`NotUsedWhen`, `DependentOn`) means "search the whole payload/definition set for this name" -
  wrong for a column name that repeats once per row (e.g. `EmissionsCalculationCycle` appears
  identically in every row); reusing `Field` would silently resolve the wrong row's value, not
  just be ambiguous. `Column` = "look at the sibling cell in THIS row".
- Evaluator: does NOT go anywhere near the existing `NotUsedWhen`/`DependentOn` evaluators (both
  are unrelated - whole-payload search or UI-only, no row context, no `Contains` predicate today).
  Purely additive, evaluated INLINE in each RowsToCols table write loop, at the point
  `$allowFormulaOverwrite` already gets computed - because that's the only place the full row
  object (this script's `$entryData`, `create-test-excel-from-json.ps1:1475`; the production
  consumer's equivalent) is actually in scope.
  - In THIS repo: `scripts/create-test-excel-from-json.ps1`'s RowsToCols write loop
    (~line 1469-1539, `$entryData` at 1475, `$allowFormulaOverwrite` computed at line 1526 via
    `Test-AllowFormulaOverwriteTableField`) - add the `CannotOverWriteFormula` check inline there,
    reading `$entryData.<Column>`. `Test-AllowFormulaOverwriteTableField`/`TableFieldAny`
    themselves stay name-only (no row context) - they're not the right place for this logic.
  - `Add-OverwritePolicyFromInputFieldDefinition` (builds the static per-name HashSets from the
    InputFields JSON) already defensively checks both `CanOverWriteFormula` and misspelled
    `CanOverwriteFormula` (line 589-592) - unaffected by this change, still handles the static
    `true`/`false` case; `CannotOverWriteFormula` is read separately, inline, at write time.
- v1 scope: RowsToCols tables ONLY (covers the actual ActivityPeriodEmissions/
  CarbonRemovalsFromPlantings case). ColsToRows tables (the Method1/Method2 Head/Duration/
  Liveweight/etc. named-range tables) go through a DIFFERENT, column-major write loop
  (~line 1604-1653 in this script) with no equivalent flat sibling-row object in scope -
  extending this there is explicitly deferred/harder, not started.
- Still TODO when implementing: (1) update `_schema` doc block in both `_overrides/*.json` files
  to document `CannotOverWriteFormula`; (2) replace the placeholder `{}` Columns entries on
  `CO2EEmissionsMethod1`/`CO2EEmissionsMethod2`/`CO2RemovedAttributedToThisEnterprise` in
  `_overrides/Enterprise_PastureBeef.json` with the real condition; (3) add the inline evaluator

# Text-format fallback scan (2026-08, generalises the fix above)
- The single-cell 'representative body cell' Get-CellTypeByFormat samples (row 2 of a RowsToCols named-range table, first DataBodyRange row of a ListObject column) can be blank with NO explicit format of its own, masking a column the author DID format as Text elsewhere (e.g. Table_Input_DataQuality_*'s Notes/EvidenceFiles columns, freshly authored with no data yet). Get-CellTypeByFormat now accepts an optional -FallbackRange (the REST of that field's data column/row); when the primary cell doesn't already resolve to percent/text, it scans every non-formula cell in the fallback range for an explicit Text ('@' or format text matching 'text') and uses that. Callers wire this through: Get-TableFieldDef passes the WHOLE `$Column.DataBodyRange` (ListObject); the RowsToCols/ColsToRows loops in Get-NamedRangeTables build a `$Worksheet.Range(cell1, cell2)` spanning the rest of that field's rows/columns. Single named InputCells (X_Cell_*) unchanged — no "column" to widen, the one cell's format IS the answer. Verified: Notes/EvidenceFiles stayed 'number' until the underlying Excel cell format was changed General->Text, then correctly flipped to 'text' on rebuild with zero other diffs (confirmed via full-file diff, only those keys changed).
